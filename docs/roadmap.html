Where we stopped

Email judge v2.2 is built but not measured

The judge that scores email quality went through four versions on 2026-10-09. Version 2.1 caught 69 of 70 planted flaws but gave different verdicts on the same email too often. Version 2.2 moves the tone decision into code to fix that. Paid runs are paused until we agree a cheaper way to measure it.

Cost finding: the Message Batches API takes 50% off every token. Prompt caching cannot help here because the judge prompt is about 1.5k tokens and Haiku 4.5 only caches prompts of 4,096 tokens or more.

Next, in order
  1. Agree how to measure the judge cheaply. The Batches API is the leading option.
  2. Measure judge v2.2. Report catch rate and flip rate together.
  3. Add a code check for formulaic phrasing across a batch of emails.
  4. Resume writer tuning on the fixture of 10 leads.
  5. Build the Docker image, then deploy API, worker and Redis.
  6. Week 7: review API and UI (approve, edit, reject).

Email judge versions

Catch rate is how many deliberately broken emails the judge failed. Flip rate is how often it changed its verdict on the same unedited email across three runs. Both must be good.

Known limits

  • Grounding proves a quote is on the page. It does not prove the page is honest. Injected text can be quoted and pass.
  • No auth on the API. Rate limits are per IP and weak against rotating IPs.
  • The rate-limit check and insert are not atomic, so simultaneous requests can overshoot by about one run.
  • The rubric has no criterion for templated phrasing, so the judge cannot see it.
  • This network blocks outbound ports 5432 and 6543. Migrations were applied to Supabase over HTTPS instead.
